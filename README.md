# LAW / INDEX — 法務トピック知識ベース

法令・ガイドライン・行政資料・判例・実務解説などを、個別記事ではなくテーマ単位で整理する静的知識ベースです。

## 実装していること

- 追加日順の新着記事・資料一覧
- テーマ一覧、分野フィルタ、記事検索
- 法改正記事を改正イベント単位で整理した一覧
- 要点、影響した論点、更新前 / 更新後、一次資料をまとめた更新詳細ページ
- テーマごとの独立ページ
- 現在の整理 / 論点 / 主要資料 / 更新履歴
- 確定情報・解釈/整理・実務上の示唆・未確定事項の表示分離
- テーマ名、論点、更新、資料名、所管、省庁、実務影響を対象にした知識全体検索
- 一次資料を骨格にした根拠リンク
- GitHub Pagesで公開できる静的ファイル構成

## データ構造

- `data/topics.js` — テーマ・論点・現在の整理・実務影響
- `data/sources.js` — 法令・ガイドライン・行政資料などの根拠資料
- `data/updates.js` — 公表資料、要点、影響論点、更新前後の差分を持つ更新イベント
- `data/reforms.js` — 法改正イベント。法令・制度、施行日、施行日の根拠資料を記事から独立して保持する
- `data/articles*.js` — 記事・資料。`collectedAt` は追加日、`publishedAt` は公開日。法改正記事は原則として `reformEventId` で改正イベントへ接続する
- `data/reform-policy.js` — 法改正ページで使う施行日の厳格な採用ルール。本文推測や固定 fallback を禁止する
- `topics/*.html` — テーマごとの入口ページ
- `update.html` — 更新イベントを文脈に応じて表示する共通詳細ページ

## 法令・改正イベント・記事

法改正ページでは、**法令・制度そのもの、個々の改正イベント、その改正を扱う記事を別のものとして管理します。**

たとえば「同一労働同一賃金ガイドライン等」という制度の下に「2026年改正」という改正イベントを置き、そのイベントに施行日 `2026-10-01` と一次資料を登録します。各記事は `reformEventId: "equal-pay-guideline-2026"` のようにイベントへ接続します。

施行日は記事の属性ではなく、原則として改正イベントの属性です。同じ改正を扱う記事が複数あっても、施行日とその根拠を各記事へ重複して持たせません。

既存記事は段階的に移行します。`reformEventId` がない記事も表示を維持しますが、法改正ページでは「改正イベント未整理」と表示します。これは法律上の施行日が不明という意味ではなく、LAW / INDEX 上で改正イベントへの切り分けが未完了という意味です。

## 法改正イベントの施行日

`data/reforms.js` で施行日を登録する場合は、`effectiveDate` または `effectiveDates` を明示し、その日付を確認できる一次資料を `effectiveDateSourceIds` に1件以上指定します。各 sourceId は同じイベントの `sourceIds` にも含めます。

次の方法で施行日を補完することは禁止します。

- 記事タイトル、summary、whyImportant、whatChanged、関連テーマ等の文章から日付を抽出する
- 「施行」「公布」「成立」等の語の近くにある日付を機械的に施行日とみなす
- 法令名ごとに固定した fallback 日付を当てる
- 二次資料だけを根拠に施行日を確定する

複数の施行日・適用開始日が存在する場合は `effectiveDates` を使えます。法改正一覧では、根拠確認済みの日付のうち最も遅い日付を並び順・代表表示用に採用します。これは一連の改正の残存対応期限を把握しやすくするための一覧上のルールであり、すべての規定がその日に一斉施行されることを意味しません。

旧来の記事単位の `reformEffectiveDate` / `reformEffectiveDates` / `reformEffectiveDateSourceIds` は、未移行記事との互換性のため当面読み込みます。新規データでは原則使用せず、改正イベントへ移します。

## 法改正ページの段階タグ

法改正ページで記事の公開日の右側に表示する段階タグは、**その記事が公開された時点で、その記事が扱う改正イベントがどの段階にあったか**を示します。現在の制度状態を示すタグではありません。

段階は記事データの `reformStageAtPublication` に明示し、タイトル、記事本文、関連テーマの `stage` から自動推測しません。値を付ける場合は、その段階を確認できる一次資料を `reformStageSourceIds` に1件以上指定します。確認できない場合は両フィールドを付けず、画面にもタグを表示しません。

許容値は次の4つだけです。

- `proposal` — **案・審議中**。法案、政省令案、ガイドライン案、パブリックコメント案など、正式な最終内容がまだ確定していない段階。
- `finalized_pending` — **確定・施行/適用前**。法律の成立・公布、政省令等の公布、ガイドライン等の正式公表などにより対象となる最終内容が確定しているが、その記事の公開日時点では施行日・適用開始日を迎えていない段階。
- `partially_effective` — **一部施行/適用済**。対象となる一連の改正の一部が既に施行・適用されている一方、主要な残部に将来の施行・適用日が残っている段階。
- `effective` — **施行/適用済**。その記事が扱う対象改正が記事公開日時点で施行・適用済みの段階。

`成立` と `公布`、`公布` と `施行`、`公表` と `適用開始` は同一視しません。記事タイトルにこれらの語が含まれることだけを根拠に段階を付ける運用は禁止します。また、単に「制度見直し中」「改正の議論がある」という状態は特定の改正イベントの段階ではないため、このタグでは表現しません。

## 更新日の運用

- `lastUpdated` は、テーマの要点・論点・根拠など現在の整理を実際に変更した日です。
- `lastVerified` は、関連情報を確認した最新日です。採用記事が「整理変更なし」と判定された場合、記事の `collectedAt` から関連テーマの確認日だけを進めます。
- 読み込み時に記事・更新履歴から `lastVerified` を再計算するため、テーマデータの再生成で確認日が巻き戻っても復元できます。`lastUpdated` はこの処理では変更しません。

`node scripts/validate-data.mjs` は日付の逆転、status の分布、全論点が `authoritative` のテーマ、`interpreted` / `pending` の views 未登録に加え、改正イベント、記事からイベントへの参照、段階タグ、施行日の根拠資料の整合性を監査します。`reformEventId` 未登録の既存法改正記事は警告として数え、表示は維持したまま段階的に移行します。

本文を転載せず、原文へのリンクと、現在地を確認するための整理情報を保持します。重要な判断では必ず原資料を確認してください。
