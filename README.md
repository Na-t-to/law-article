# LAW / INDEX — 法務トピック知識ベース

法令・ガイドライン・行政資料・判例・実務解説などを、個別記事ではなくテーマ単位で整理する静的知識ベースです。

## 実装していること

- 追加日順の新着記事・資料一覧
- テーマ一覧、分野フィルタ、記事検索
- 法改正記事を改正イベント単位で整理した一覧
- 要点、影響した論点、更新前 / 更新後、一次資料をまとめた更新詳細ページ
- テーマごとの独立ページ
- 現在の整理 / 論点 / 主要資料 / 更新履歴
- 確定情報・解釈/整理・実務上の示唆・未確定事項の表示分離
- テーマ名、論点、更新、資料名、所管、省庁、実務影響を対象にした知識全体検索
- 一次資料を骨格にした根拠リンク
- GitHub Pagesで公開できる静的ファイル構成

## データ構造

- `data/topics.js` — テーマ・論点・現在の整理・実務影響
- `data/sources.js` — 法令・ガイドライン・行政資料などの根拠資料
- `data/updates.js` — 公表資料、要点、影響論点、更新前後の差分を持つ更新イベント
- `data/reforms.js` — 法改正イベント。法令・制度、イベント種別、施行時期、根拠資料、既存記事との対応を記事から独立して保持する
- `data/articles*.js` — 記事・資料。`collectedAt` は追加日、`publishedAt` は公開日。新規の法改正記事は原則として `reformEventId` で改正イベントへ接続する
- `data/reform-policy.js` — 法改正ページで使う施行時期の厳格な採用・表示ルール。本文推測や固定 fallback を禁止する
- `topics/*.html` — テーマごとの入口ページ
- `update.html` — 更新イベントを文脈に応じて表示する共通詳細ページ

## 法令・改正イベント・記事

法改正ページでは、**法令・制度そのもの、個々の改正イベント、その改正を扱う記事を別のものとして管理します。**

たとえば「同一労働同一賃金ガイドライン等」という制度の下に「2026年改正」という改正イベントを置き、そのイベントに施行日 `2026-10-01` と一次資料を登録します。新規記事は `reformEventId: "equal-pay-guideline-2026"` のようにイベントへ明示接続します。

既存記事を棚卸しする場合は、全記事へ `reformEventId` を書き戻さなくても、改正イベントの `matchSourceIds` にその改正イベントを識別できる一次資料の sourceId を指定できます。記事の `primarySourceIds` と一意に一致した場合だけ、そのイベントへ整理します。複数イベントに一致する場合は自動で決めず、検証エラーとして人がイベント境界を見直します。

`matchSourceIds` は単なる同一法令の資料ではなく、**同じ改正イベントを識別できる資料**に限ります。現行法全文、一般ポータル、複数改正にまたがる資料などを広く指定して、法律名だけで記事を束ねる運用は禁止します。

## 法改正イベントの種類

`eventType` は次の値を使います。

- `law_amendment` — 既存法律の改正
- `new_law` — 新法・新制度の制定
- `regulation_or_guideline` — 政省令、告示、法定指針等の改正・制定で、独立して施行・適用時期を管理する価値があるもの
- `policy_review` — 制度見直し自体を独立イベントとして追う必要がある場合。単なる研究会・検討会資料を機械的に登録しない

新法や改正法と、その後の個別の下位法令改正をどこまで同一イベントに含めるかは、企業の対応事項と施行時期が一体として管理できるかで判断します。同じテーマでも独立した対応期限を持つ改正は別イベントに分けます。一方、一つの記事が一連の制度改正をまとめて扱い、記事単位で分割するとかえって誤解を生む場合は、`phased` の一つのイベントとして扱えます。

## 施行時期の状態

施行時期は `effectiveDateStatus` で意味を分けます。

- `confirmed` — 法令・告示等で施行日・適用開始日が確定している。画面では **「施行日」** と表示する
- `planned` — 案・パブリックコメント等で具体的な施行予定時期が示されているが、まだ最終確定していない。画面では **「施行予定」** と表示する
- `relative` — 「公布後2年以内の政令で定める日」など、具体的な暦日が未確定の相対期日。`effectiveDateNote` にその内容を明示する
- `phased` — 一つの改正イベントの規定が複数時点に分けて施行・適用される。`effectiveDates` と `effectiveDateNote` を使って段階施行であることを明示する

`confirmed` と `planned` を同じ「施行日」として表示しません。また、`relative` を推測した暦日に変換しません。

`effectiveDate` / `effectiveDates` を登録する場合、その日付を確認できる一次資料を `effectiveDateSourceIds` に1件以上指定します。相対期日や段階施行でも、その施行時期の記述を確認できる一次資料を `effectiveDateSourceIds` に指定します。各 sourceId は同じイベントの `sourceIds` にも含めます。

次の方法で施行時期を補完することは禁止します。

- 記事タイトル、summary、whyImportant、whatChanged、関連テーマ等の文章から日付を抽出する
- 「施行」「公布」「成立」等の語の近くにある日付を機械的に施行日とみなす
- 法令名ごとに固定した fallback 日付を当てる
- 二次資料だけを根拠に施行時期を確定する

旧来の記事単位の `reformEffectiveDate` / `reformEffectiveDates` / `reformEffectiveDateSourceIds` は、未整理記事との互換性のため当面読み込みます。新規データでは原則使用せず、改正イベントへ移します。

## 法改正ページの段階タグ

法改正ページで記事の公開日の右側に表示する段階タグは、**その記事が公開された時点で、その記事が扱う改正イベントがどの段階にあったか**を示します。現在の制度状態を示すタグではありません。

段階は記事データの `reformStageAtPublication` に明示し、タイトル、記事本文、関連テーマの `stage` から自動推測しません。値を付ける場合は、その段階を確認できる一次資料を `reformStageSourceIds` に1件以上指定します。確認できない場合は両フィールドを付けず、画面にもタグを表示しません。

許容値は次の4つだけです。

- `proposal` — **案・審議中**。法案、政省令案、ガイドライン案、パブリックコメント案など、正式な最終内容がまだ確定していない段階
- `finalized_pending` — **確定・施行/適用前**。法律の成立・公布、政省令等の公布、ガイドライン等の正式公表などにより対象となる最終内容が確定しているが、その記事の公開日時点では施行日・適用開始日を迎えていない段階
- `partially_effective` — **一部施行/適用済**。対象となる一連の改正の一部が既に施行・適用されている一方、主要な残部に将来の施行・適用日が残っている段階
- `effective` — **施行/適用済**。その記事が扱う対象改正が記事公開日時点で施行・適用済みの段階

`成立` と `公布`、`公布` と `施行`、`公表` と `適用開始` は同一視しません。記事タイトルにこれらの語が含まれることだけを根拠に段階を付ける運用は禁止します。また、単に「制度見直し中」「改正の議論がある」という状態は特定の改正イベントの段階ではないため、このタグでは表現しません。

## 更新日の運用

- `lastUpdated` は、テーマの要点・論点・根拠など現在の整理を実際に変更した日です。
- `lastVerified` は、関連情報を確認した最新日です。採用記事が「整理変更なし」と判定された場合、記事の `collectedAt` から関連テーマの確認日だけを進めます。
- 読み込み時に記事・更新履歴から `lastVerified` を再計算するため、テーマデータの再生成で確認日が巻き戻っても復元できます。`lastUpdated` はこの処理では変更しません。

`node scripts/validate-data.mjs` は、日付の逆転、status、views に加え、改正イベントの `eventType` / `effectiveDateStatus`、施行時期の根拠、`matchSourceIds`、記事との一意な対応、段階タグを監査します。イベントへ一意に整理できない既存の法改正記事は「改正イベント未整理」として表示を維持し、無理に分類しません。

本文を転載せず、原文へのリンクと、現在地を確認するための整理情報を保持します。重要な判断では必ず原資料を確認してください。
